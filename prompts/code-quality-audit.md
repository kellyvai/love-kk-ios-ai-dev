# 代码质量审查框架

检查代码的健康度、是否遵循项目约定、是否有技术债。

---

## 审查维度

### 1. 代码遵循性

**检查项：**
- [ ] 是否遵循 CLAUDE.md 中的约定
- [ ] 是否有不该修改的文件被修改了
- [ ] 命名约定是否一致
- [ ] 代码风格是否一致

### 2. 重复代码和提取机会

**检查项：**
- [ ] 是否有相同的逻辑在多个地方重复
- [ ] 是否有可以提取为通用组件的代码
- [ ] 是否有完全相同的 UI 模式
- [ ] 是否有重复的计算逻辑

**衡量标准：** 同样的逻辑出现 3 次以上就应该提取

### 3. 状态管理混乱

**检查项：**
- [ ] 状态定义是否完整（在 CLAUDE.md 中）
- [ ] 是否有组件之间的状态互相干扰
- [ ] 是否有多个组件管理相同的状态
- [ ] 是否有状态转移没有对应的处理

**红旗信号：**
- ❌ 同一个数据在多个组件中有多份 copy
- ❌ 状态更新时某些页面没有反应
- ❌ 状态定义在组件深处，难以追踪

### 4. 异步操作完整性

**检查项：**
- [ ] 是否所有异步操作都有 loading 状态
- [ ] 是否都有 error 处理
- [ ] 是否都有 finally 块来释放锁和清理资源
- [ ] 是否防止重复提交

**必备三件套：**
```
const [loading, setLoading] = useState(false);

const handleSave = async () => {
  if (loading) return; // 防重复
  setLoading(true);
  try {
    await saveData();
    // 成功处理
  } catch (err) {
    // 错误处理
  } finally {
    setLoading(false); // 必须有
  }
};
```

### 5. 内存泄漏风险

**检查项：**
- [ ] 是否有未清理的事件监听器
- [ ] 是否有未取消的 setTimeout/setInterval
- [ ] 是否有订阅没有取消
- [ ] 组件卸载时是否清理资源

### 6. 类型安全

**检查项：**
- [ ] TypeScript 类型是否完整（没有 `any`）
- [ ] API 响应是否有类型定义
- [ ] Props 是否有完整的类型定义
- [ ] 是否有类型检查错误

## 审查工作流

### 步骤 1：遵循性检查

```
对比清单：
- CLAUDE.md 中定义的状态结构 vs 实际代码
- CLAUDE.md 中的禁区列表 vs 实际修改的文件
- 约定的命名规则 vs 实际命名
```

### 步骤 2：代码指标分析

```
关键指标：
- 平均函数长度（应该 < 50 行）
- 最深嵌套层级（应该 < 4 层）
- 重复代码比例（应该 < 10%）
- 类型错误数量（应该 = 0）
```

### 步骤 3：模式识别

扫描常见的代码反模式：

```
反模式检查清单：
- [ ] 在 useEffect 中没有依赖数组
- [ ] 有空的 useEffect 依赖数组（只会执行一次）
- [ ] 在渲染时创建新对象/函数导致不必要的重渲染
- [ ] 同一组件有多个 useState 管理相关状态
- [ ] 没有用 memo/useMemo 优化性能关键的渲染
- [ ] 异步操作没有 loading 状态
- [ ] 没有错误处理
- [ ] API 调用硬编码了 URL
- [ ] 没有验证用户输入
```

### 步骤 4：问题分类

```
【问题】：重复的数据转换逻辑
- 位置：pages/Baby.tsx、pages/Growth.tsx、components/BabyList.tsx
- 问题：同样的「日期格式化」逻辑在 3 个地方重复
- 改进建议：提取为 `utils/dateFormatters.ts`，所有地方导入使用
- 优先级：🟡 次要（技术债，不影响功能）

【问题】：缺少异步操作的 finally 清理
- 位置：components/SaveButton.tsx, line 45
- 问题：保存操作没有在 finally 中释放 loading 状态
- 影响：如果出错，按钮永久处于 loading 状态
- 修复：添加 finally { setLoading(false) }
- 优先级：🔴 关键（影响功能正常使用）
```
