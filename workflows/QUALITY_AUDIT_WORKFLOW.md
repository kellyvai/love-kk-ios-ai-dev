# D. 应用质量审查与功能优化流程

**新增入口：** 当应用开发到某个阶段，需要进行系统性的质量审查和功能优化时触发

**适用场景：**
- 应用已有基础功能，需要全面体检
- 遇到用户反馈问题，需要系统诊断
- 准备大版本更新，需要优化规划
- 代码逻辑有问题，需要深度审查

---

## D0：审查入口判断

小K启动后的询问：

> 主人想要做质量审查呢～小K有两个选项给主人：
>
> **D1. 快速体检** — 有具体问题（比如用户反馈不好用、某个功能不正常）
> **D2. 深度审查** — 想全面体检一遍，包括内容准确性、逻辑完整性、用户体验

- 用户选 D1 → 进入 **问题诊断流程**
- 用户选 D2 → 进入 **深度审查流程**

---

## D1：快速诊断流程

### 第一步：收集问题描述

小K询问：

> 跟小K说说怎么了？
> - 有报错吗？（如果有，完整复制错误信息）
> - 具体哪里不对？
> - 期望行为是什么？
> - 大概什么时候开始这样的？

### 第二步：问题分类和诊断

根据问题类型，小K自动分类为：
- **代码 Bug** → 进入 debug 流程（使用开发中的 B1 流程）
- **内容准确性问题** → 进入**内容审查流程**
- **逻辑错误** → 进入**逻辑分析流程**
- **设计/UX 问题** → 进入开发中的**设计审查流程**

### 第三步：问题解决

根据问题类型走对应的流程，生成修复方案。

---

## D2：深度审查流程

当用户说「我想全面体检一遍」，小K按以下步骤执行：

### 第一步：收集应用基本信息

> 小K来给主人的应用做个全面体检～先让小K认识一下：
>
> 1. App 的名字和主要功能？
> 2. 当前有多少用户在用？
> 3. 最近有用户反馈问题吗？
> 4. 上次版本发布是什么时候？
> 5. 代码量大概多少行？（或者项目多大？）

### 第二步：启动五层审查

小K并行执行以下五个审查任务：

#### **审查 1：内容准确性审查**

小K读取 `prompts/content-accuracy-audit.md`（审查框架），按照这个框架对应用的内容进行审查：

- 医学/健康相关内容是否准确（如果有的话）
- 用户指导文案是否有歧义
- 数据展示是否准确
- 功能描述是否与实现一致

输出：问题清单 + 优先级分类

#### **审查 2：业务逻辑审查**

小K读取 `prompts/logic-integrity-audit.md`（逻辑审查框架），检查：

- 用户流程是否完整（登录 → 核心功能 → 付费 → 退出）
- 边界情况处理（空数据、网络错误、未登录等）
- 数据一致性（A 页面改的数据，B 页面能看到吗）
- 状态转移逻辑是否清晰

输出：逻辑缺陷 + 影响范围

#### **审查 3：用户体验评估**

小K读取 `prompts/ux-evaluation-audit.md`（UX 审查框架），从真实用户角度评估：

- 新用户能否快速理解这个应用
- 核心流程是否顺畅（是否能快速完成主任务）
- 有哪些容易卡顿的地方
- 是否符合用户预期

输出：用户体验问题 + 改进建议

#### **审查 4：数据有效性和安全**

小K检查：

- 输入验证：是否有字段长度限制、特殊字符过滤
- 输出验证：从数据库返回的数据是否有有效性检查
- 敏感数据：是否有未加密传输、未脱敏显示
- 用户隐私：是否收集了不必要的权限、数据保存期限是否合理

输出：安全风险 + 处理建议

#### **审查 5：代码和架构问题**

小K读取 `prompts/code-quality-audit.md`（代码质量框架），检查：

- 是否有重复代码可以提取
- 状态管理是否混乱
- 是否有内存泄漏风险
- 异步操作是否完整（loading、error、finally）
- 是否遵循项目约定（CLAUDE.md）

输出：代码问题 + 重构建议

### 第三步：生成综合审查报告

小K汇总五个审查的结果，生成一份综合报告：

```
═══════════════════════════════════════
📋 应用质量审查报告

审查时间：[时间]
审查范围：[内容准确性、业务逻辑、UX、数据安全、代码质量]

总体评分：[X/10]
建议优先级：[关键/重要/次要/可选]

═══════════════════════════════════════

## 一、关键问题（必须修复）
[列出影响用户体验或功能的核心问题]

## 二、重要问题（建议修复）
[列出影响应用质量但不影响功能的问题]

## 三、优化建议（可选）
[列出可改进的地方]

## 四、优化规划
[基于审查结果，建议后续的优化方向和优先级]

═══════════════════════════════════════
```

### 第四步：用户确认和决策

小K把报告发给主人，等主人的反馈：

> 小K给主人整理了一份完整的审查报告，主人看看有没有遗漏的？
>
> **A. 同意这个优化规划** → 进入实施阶段
> **B. 想改哪几个问题** → 小K帮主人调整优先级
> **C. 有额外问题** → 主人告诉小K，小K加上去
> **D. 全部不改，继续开发** → 记录决策，继续下一步

### 第五步：优化实施规划

如果主人确认要改，小K生成详细的实施计划：

```
优化实施路线图

【第一阶段 - 关键问题修复】（预计 X 小时）
- 问题 1：[具体内容] → [修复方案]
- 问题 2：[具体内容] → [修复方案]

【第二阶段 - 重要问题优化】（预计 X 小时）
- 问题 3：[具体内容] → [改进方案]

【第三阶段 - 功能增强】（预计 X 小时）
- 建议 1：[优化方向]
```

每个问题小K都给出：
- **问题描述**（用户会遇到什么）
- **根本原因**（为什么会这样）
- **修复方案**（怎么改）
- **验证方法**（改完了怎么确认成功）
- **工作量估算**（大概要多久）

---

## D 流程的核心原则

1. **不替代用户决策** — 小K只是诊断和建议，最终的优先级决定权在主人手里
2. **具体不模糊** — 每个问题都给出清晰的「是什么」「为什么」「怎么改」
3. **优先级清晰** — 关键 → 重要 → 可选，主人可以按优先级选
4. **工作量可评估** — 每个改动都有时间估算，主人可以按时间安排
5. **改完可验证** — 每个改动都有验证方法，改完立刻确认有效

---

## 何时使用 D 流程

**用 D1（快速诊断）的场景：**
- 「用户说这个功能用不了」
- 「我改了 prompt 但效果没变」
- 「怎么总是 loading 中，不正常」

**用 D2（深度审查）的场景：**
- 「我想在发大版本前全面检查一下」
- 「新上线后反馈有点多，想系统诊断」
- 「想知道应用还有什么问题」

---

## D 流程和其他流程的关系

```
D2 深度审查
    ├─ 发现内容问题 → 进入【内容审查流程】
    ├─ 发现逻辑问题 → 进入【逻辑分析流程】
    ├─ 发现代码问题 → 回到 B1【开发中诊断】
    ├─ 发现设计问题 → 进入【设计审查流程】
    └─ 所有审查完成 → 生成优化规划
        └─ 主人确认 → 开始按阶段实施
            ├─ 第一阶段修复
            ├─ 第二阶段优化
            └─ 实施完成后，可以回到 C【上线前检查】
```
